## Design Brief

A short alignment checkpoint. If the direction below is wrong, it is much cheaper to say so
here than after the plan and the scopes are built on it.

### Current State

The registry is **half-built, not missing**. `internal/experience/` already ships a
generated, content-free catalog: `catalog.gen.json` under schema
`smackerel-product-experience/v1`, 20 surfaces, produced by `./smackerel.sh config generate`
from the `product_experience` block in `config/smackerel.yaml` and embedded via `//go:embed`.
It already has a validator, a navigation projection, a renderer projection, a consumer
inventory, and state and mutation presenters.

Every one of those 20 surfaces carries a `capability_id` (`cap.assistant`, `cap.today`,
`cap.search`, …). **Nothing is on the other end of that reference.** `config/smackerel.yaml`
has no `capabilities:` block; the ids are a foreign key into a table that does not exist.
The validator anticipated this — `RouteInventory.KnownCapabilities` exists and
`unknown-capability` is already an emitted violation (`internal/experience/validator.go:99`)
— but a nil map disables the check, and the only production-shaped consumer builds the map
with `iCapsOf(cat)` from the catalog under validation
(`tests/integration/experience/route_inventory_test.go:92-100`). The check is circular and
cannot fail.

Separately, four reachability inventories are hand-maintained and have already drifted:
`config/assistant/scenarios.yaml` (5 user-facing intents), `internal/web/appshell.go` +
`web/pwa/lib/appnav.js` + `internal/web/templates.go` (three navigation authorities, one
carrying a false "mirrors" comment), `internal/assistant/shortcuts.go` (a slash table that
contradicts the intent registry on `/ask`, `/recipe`, `/cook`), and the not-yet-built MCP
tool list (spec 109).

### Target State

Add a **`capabilities:` block as a sibling of `surfaces:` inside the same
`product_experience` SST block**, generated by the same `config generate` path into the same
`catalog.gen.json`, at a bumped schema version. `Surface.CapabilityID` becomes a resolvable
foreign key. Each reachability surface becomes a projection of that capability set. The
coverage check compares the capability set against a universe derived by **re-running the
running system's own discovery code paths**, never from the catalog.

### Patterns To Follow

- **Closed vocabularies with a `valid()` method and no usable zero value.** `SurfaceKind`,
  `Renderer` and `DiscoverabilityPolicy` in `internal/experience/catalog.go` all do this;
  `""` is rejected rather than defaulted. Exposure class and side-effect class follow it.
- **Generated-from-SST, embedded, never handwritten.** `config/smackerel.yaml` →
  `scripts/commands/config.sh` (line ~3172) → `catalog.gen.json` → `//go:embed`. The
  capability block joins this path; it does not get a second one.
- **Fail-closed typed violation lists with deterministic ordering.** `F106RouteDrift`
  accumulates every violation and sorts for stability rather than short-circuiting.
- **Universe-by-probe.** `route_inventory_test.go` derives `RegisteredPaths` by probing the
  live server and treating any non-404 as registered. That is a genuinely independent
  universe and is the template `D2` generalises.
- **Startup-resolved enforcement stage.** `internal/api/corpus_grant_gate.go` resolves
  `observe` / `enforce` once at process start from SST and exposes `Mode()`. The projection
  admission predicate consumes exactly this.

### Patterns To Avoid

- **`iCapsOf(cat)`** (`route_inventory_test.go:92-100`). Building the expected universe from
  the artifact under test. It is the single pattern this feature exists to eliminate, and it
  is currently the *only* production-shaped feed of `KnownCapabilities`.
- **The "ALONGSIDE" posture.** `internal/experience/catalog.go:10` records that the generated
  catalog was added beside the still-active handwritten authorities with cutover deferred.
  That was correct as a slice boundary in spec 106 and is a defect as an end state (P2).
- **A second registry.** Anything that authors capability identity or capability policy
  outside the extended catalog. Non-Goal 1, Principle 5.
- **The `unavailable_pending_*` presentation pattern, for grant-withheld capabilities.** It
  keeps the label and drops the href. That is right for "not built yet" and wrong for "you
  are not permitted to know this exists" (NFR-112-06). See `D10`.
- **Deriving the external tool list from `agent.All()`.** Spec 109 forbids it by name.

### Resolved Decisions

- A capability is a **declared record with a `cap.*` id**, not a prompt contract and not a
  surface. Contracts bind to it 0..N; a contract binds to at most one capability (`D1`).
- The coverage universe is the **union of three independent producers**, none of which may
  import the registry package (`D2`).
- The descriptor is a `capabilities:` sibling of `surfaces:` at schema `v2` (`D3`).
- Exposure vocabulary is five closed values with a required reason for the four
  non-user-facing ones (`D4`).
- `/ask` resolves to `open_knowledge`; `/recipe` and `/cook` are kept (`D5`).
- The navigation cutover stays with spec 106; 112 declares and validates the core (`D6`).
- The external projection is opt-in per descriptor, absent by default (`D7`).
- The core guarantee is asserted **per renderer**, which is what makes it falsifiable (`D8`).
- Grant-requiring capabilities are withheld by a **runtime predicate** on spec 108's
  resolved stage, not by waiting for spec 108's schedule (`D9`).
- Withholding is silent in the projection and loud on an operator-only channel (`D10`).

## Decision Record

Each entry records the decision, the alternatives weighed, the reasoning, and the
consequence. The two BLOCKING-backed decisions come first.

### D1 — What constitutes one capability, and how contracts bind · `F-112-UNIT-01` (BLOCKING)

**Decision.** A **capability is a declared record**, identified by a stable `cap.*` id,
authored in the `capabilities:` block. It is neither a prompt contract nor a catalog surface.
Binding is explicit and directional:

- A capability declares `contracts: []` — **zero or more** prompt-contract ids.
- A prompt contract binds to **at most one** capability. Two capabilities claiming the same
  contract is a coverage-check violation (`contract-claimed-twice`).
- A capability declares `surfaces: []` — zero or more catalog surface ids — and the reverse
  edge `Surface.CapabilityID` must agree with it. Disagreement is a violation
  (`capability-surface-edge-mismatch`).

The three binding shapes that follow are all legitimate and all real today:

| Shape | Meaning | Example from the tree |
|---|---|---|
| 0 contracts, ≥1 surface | A navigable capability with no dispatchable contract | `cap.settings`, `cap.today` |
| 1 contract, 0..N surfaces | The ordinary dispatchable capability | `retrieval_qa`, `weather_query` |
| N contracts, 0..N surfaces | One user-visible function served by several contracts | the four `recommendation_*` contracts |

**Alternatives considered.**

1. *Capability ≡ prompt contract.* Rejected. It cannot describe `cap.settings` or
   `cap.today`, which have no contract at all, so 20 of the 20 existing `capability_id`
   values would have no record. It also forces the ten pipeline stages (E3) into the same
   unit as the eleven dispatchable ones, which is precisely the conflation the `D17`
   sharpening identified.
2. *Capability ≡ catalog surface.* Rejected symmetrically. Surfaces are navigation nodes;
   `retrieval_qa` is dispatchable and has no surface of its own. It would also make
   `Surface.CapabilityID` a self-reference, which is not a foreign key.
3. *Capability ≡ the union, inferred.* Rejected because inference is what the repository
   already cannot do — nothing today records whether a contract is unsurfaced deliberately
   or by omission (`spec.md` §3). An inferred unit reproduces exactly that.
4. *Contract binds to many capabilities.* Rejected. It re-opens the "one fact written down
   twice" defect at a new granularity: two capabilities sharing a contract would each
   declare that contract's exposure, authorization and provenance, and they could disagree.

**Reasoning.** The registry's job is to make exposure a *declared* fact. Only a declared
record can span a navigable-but-not-dispatchable surface and a dispatchable-but-not-navigable
contract, which is the actual shape of the system. The at-most-one-owner rule on the contract
edge is what stops the declaration from fragmenting: every contract has exactly one place its
policy is authored, which is P1 restated at the binding level rather than only at the record
level.

**Consequence.** The capability count is an authored number, not `27 − 5` and not `11`.
Expect roughly the 20 existing `cap.*` ids plus one per dispatchable contract not already
covered by one, minus any merged under a shared function. `SCOPE-01` builds the record and
both edges; `SCOPE-08` enforces the two edge invariants. Contract-level facts that already
exist (`IntentExamples`, `SideEffectClass` on `agent.Scenario`) are **referenced, not
re-authored** — see `## Identity, Binding, And The No-Restatement Rule`.

### D2 — How the independent universe is derived · `F-112-UNIVERSE-01` (BLOCKING)

**Decision.** The coverage check's universe is the **union of three producers, each of which
re-runs a discovery path the running system already uses**, and **none of which may import
the registry package**. The import prohibition is the mechanical form of "independent" and is
itself testable.

| Producer | Derivation | Independent because |
|---|---|---|
| **(a) Dispatchable** | `agent.Loader.Load(contractsDir, glob)` over the real contract directory, keeping registrations | It is the exact code path (`loader.go:120-228`) the process uses to decide what is dispatchable: `type: "scenario"`, id matching `^[a-z][a-z0-9_]*$`, version-slug agreement. If the loader would route it, it is in the universe. |
| **(b) Navigable** | Live registered-path probe: request each path, treat non-404 as registered | Already the established pattern for `RegisteredPaths` (`route_inventory_test.go`, `probe`/`registered`). It reads the running router, not any authored list. |
| **(c) Structurally non-dispatchable** | The same contract directory scan, keeping files whose `type != "scenario"` | Same source, complementary filter. Makes a pipeline stage a *present* member of the universe carrying a non-dispatchable marker, rather than an absence indistinguishable from an omission (R-112-15). |

The check then asserts **both directions**, which is what makes it a check rather than a
formality:

- `universe \ registry` — a built capability absent from the registry entirely (R-112-32,
  SCN-112-E05). This is the direction `iCapsOf` can never fail, because its universe is the
  registry.
- `registry \ universe` — a descriptor naming something the built system does not have
  (`phantom-capability`). Not required by a numbered requirement, and included anyway: a
  registry that can name a capability nothing implements will drift into fiction the first
  time something is deleted.

**Alternatives considered.**

1. *Feed `KnownCapabilities` from the capability block and call it independent.* Rejected —
   and this is the trap worth naming, because it looks like a fix. It is legitimate for the
   **surface→capability** reference check (there the capability records are authored and the
   surfaces are the artifact under test, so it is a real foreign-key check). It is circular
   for the **coverage** check, whose artifact under test *is* the capability set. Two
   consumers, two universes; conflating them re-creates E9 one layer up.
2. *A hand-maintained expected list.* Rejected. It is a fifth hand-maintained inventory,
   which `spec.md` §2 names as the feature's failure condition verbatim.
3. *Reflection over registered Go symbols.* Rejected. It answers "what code exists", not
   "what the system will route", and would drift from the loader's actual admission rules
   the moment those rules change.
4. *Static parse of the contract YAML by a bespoke parser.* Rejected in favour of calling the
   real loader. A second parser is a second source of truth about what a contract means, and
   it would pass while the real loader rejected the file.

**Reasoning.** "Independent" is not a property of a data structure, it is a property of the
derivation path. A universe is independent when nothing on its path reads the artifact under
test. Producers (a) and (c) read contract files; producer (b) reads the live router. The
registry is on none of those paths, and the no-import rule keeps it off them.

**Consequence.** `SCOPE-08` owns all three producers plus the no-import assertion. Producer
(b) requires a live stack, so the coverage check is an `integration`-category test, not a
`unit` one — the Test Plan in [`scopes.md`](scopes.md) already places "Independent universe"
at `integration`, which agrees. R-112-33 (a check that did not run is a failure) matters
specifically because producer (b) can skip when no stack is present: the skip must be
reported as a failure of the check, not as an absent result.

### D9 — Ordering against spec 108 and spec 109 · `F-112-108-01` (BLOCKING)

**Decision.** 112 consumes spec 108's **resolved enforcement stage**, not merely its
vocabulary, and does so as a **runtime admission predicate** rather than as a delivery
schedule. Concretely, for any capability whose descriptor declares a grant:

```
surfaced(capability) ⇔ exposure permits it
                     ∧ every declared grant is in the known grant vocabulary
                     ∧ corpusGrantStage == "enforce"
```

The third conjunct reads the stage that `internal/api/corpus_grant_gate.go` already resolves
once at process start (`corpusGrantModeObserve` / `corpusGrantModeEnforce`, `Mode()`), which
in turn is driven by the SST key `corpus_grant_enforcement` and the `corpusGrantEnforcement`
flag. While the stage is `observe`, grant-requiring capabilities are **withheld from every
projection**.

Spec 109 is treated in the opposite direction: 112 **produces** the external projection and
109 **consumes** it. 112 does not depend on 109 existing. An unconsumed projection is inert.

**Alternatives considered.**

1. *Block 112's delivery until spec 108 reaches ENFORCE.* Rejected. Spec 108's remaining
   work is three operator-owned, time-bound items — a ≥14-day OBSERVE window, proactive
   rotation of principals whose grants are unknowable, and a go/no-go denial set. None is
   code. Serialising 112 behind a calendar produces no additional safety, because the safety
   property required by P4 is about the moment of *surfacing*, not the moment of *building*.
2. *Surface grant-requiring capabilities in OBSERVE and rely on 108 counting the would-be
   denials.* Rejected outright. OBSERVE counts; it does not refuse. Surfacing a capability
   whose guard only observes is the literal reading of "reach outruns the guard" (P4), and
   `spec.md` §2 names a wider attack surface as a failure condition.
3. *112 defines its own enforcement switch.* Rejected. Two switches for one boundary is
   R-112-26 violated ("consumed from the owning specification, MUST NOT be redefined") and
   would let 112 surface capabilities 108 is still observing.

**Reasoning.** This converts a scheduling dependency into a mechanical one, which is
strictly stronger. Under a schedule, P4 holds because someone sequenced the work correctly.
Under a predicate, P4 holds because the projection cannot emit the capability — and that
survives a re-ordering, a rollback, and a deployment where the flag was never flipped.

**Consequence.** `SCOPE-03` can be built and tested against both stages before 108's flip;
its DoD item "a capability whose declared grant the running system cannot enforce is not
surfaced" becomes directly testable *today*, because the running stage is `observe` today.
`F-112-108-01` stops gating construction and instead gates the observable outcome. Severity
reclassification remains `bubbles.plan`'s call, per the finding's own text; this design does
not downgrade it.

### D3 — How the descriptor extends the existing catalog

**Decision.** Add `capabilities:` as a **sibling of `surfaces:` inside the same
`product_experience` block** of `config/smackerel.yaml`; extract it in the same
`scripts/commands/config.sh` step that already extracts `product_experience.surfaces`; emit
it into the same `internal/experience/catalog.gen.json`; embed it through the same
`//go:embed`. `ProductExperienceCatalog` gains a `Capabilities []Capability` field.
`Surface.CapabilityID` becomes a foreign key resolved against it. Schema version moves to
`smackerel-product-experience/v2`.

**Alternatives considered.**

1. *A separate `capabilities.gen.json` in the same package.* Rejected. Two generated files
   can be regenerated separately and drift between regenerations; one file cannot.
2. *A separate `config/capabilities.yaml` SST file.* Rejected. It is a second SST surface for
   one model, and the generation step would have to reconcile two inputs — the shape
   Non-Goal 1 forbids, arriving by a different route.
3. *A new Go package `internal/capability/`.* Rejected. The moment capability identity lives
   outside `internal/experience/`, `Surface.CapabilityID` points across a package boundary
   and the two can be validated separately, which is the "beside, not extending" failure.
4. *Keep schema at `v1` and add the block additively.* Rejected. `GeneratedCatalog()` already
   rejects an empty `schema_version`, and consumers key off it. A silently-changed shape
   under an unchanged version is undetectable by exactly the consumers that need to detect
   it.

**Reasoning.** "Extend, never duplicate" (P5) has to be enforced by something other than
intent. Same SST block, same generator step, same output file, same embed, same package,
same validator means there is **no seam** at which a second registry could form. A reviewer
does not have to notice the duplication; there is nowhere to put it.

**Consequence.** `GeneratedCatalog()` gains a capability non-emptiness check symmetric to its
existing zero-surfaces check. The `KnownCapabilities` seam is fed in production from
`catalog.Capabilities` — legitimate here per `D2` alternative 1, because for the
surface→capability check the capabilities are the authored side and the surfaces are the
artifact under test. Schema `v2` is a coordinated change to the generator, the embed
consumer, and every test asserting `v1`.

### D4 — The exposure-class vocabulary and its reason requirement

**Decision.** A closed vocabulary of five, modelled exactly on the existing
`DiscoverabilityPolicy` pattern (typed string, `valid()` method, no usable zero value):

| Class | Meaning | Reason required |
|---|---|---|
| `user_facing` | Reachable on demand by a daily user | no |
| `operator_only` | Reachable, but only by an operator principal | **yes** |
| `internal` | Invocable by the system, deliberately not offered to any principal | **yes** |
| `pipeline_stage` | Structurally non-dispatchable; a step inside another capability | **yes** |
| `test_only` | Exists to exercise the system; never in any user-facing projection | **yes** |

`exposure_reason` is a non-empty string, required for the four non-`user_facing` classes and
rejected as meaningless whitespace. The YAML key `exposure` is **required** — an absent key is
a generation error, not a default.

**Alternatives considered.**

1. *A boolean `user_facing`, as `config/assistant/scenarios.yaml` uses today.* Rejected. A
   boolean cannot distinguish "deliberately internal" from "pipeline stage" from "test
   harness", which is the distinction the `D17` sharpening showed the repository cannot
   currently make.
2. *Three classes (`user_facing`, `internal`, `test_only`).* Rejected. It folds
   `pipeline_stage` into `internal`, and R-112-15 requires a structurally non-dispatchable
   unit to be *identifiable as such*, not merely non-exposed.
3. *An open string with a lint.* Rejected. A lint over an open vocabulary is a fifth
   hand-maintained list of acceptable values.
4. *Default to `internal` when absent.* Rejected explicitly — it is R-112-17 inverted, and it
   restores "not listed means invisible", which P3 exists to abolish.

**Reasoning.** The `valid()`-method pattern is already the reviewer's muscle memory in this
package, and it makes the "no undeclared state" requirement a type property rather than a
convention. Requiring the reason for `operator_only` as well as the obvious three is
deliberate: an operator-only capability is the one most likely to be classified by habit.

**Consequence.** `SCOPE-02` owns the vocabulary and the reason rule. It does **not** decide
which class each of the eleven receives — that is `OD-112-01`, per `spec.md` Non-Goal 4.

### D5 — The `/ask`, `/recipe` and `/cook` contradictions · `F-112-ALIAS-01`

**Decision.** In both cases, **the shipped behaviour is authoritative and the registry entry
is the stale side**:

- `/ask` → `open_knowledge`. `retrieval_qa`'s `slash_shortcut` becomes empty.
- `/recipe` and `/cook` are both **kept**, both bound to `recipe_search`. The
  "frozen at `/ask`, `/weather`, `/remind`, `/reset`" comment in
  `config/assistant/scenarios.yaml` is retired as a stale planning constraint.

The governing invariant, which is what generation actually enforces: **many aliases may name
one capability; one alias may never name two.** `/recipe` and `/cook` both naming
`recipe_search` is legal. `/ask` naming both `open_knowledge` and `retrieval_qa` is the
defect.

**Alternatives considered.**

1. *`/ask` → `retrieval_qa`, honouring the registry.* Rejected. `internal/assistant/shortcuts.go:42-47`
   carries a dated, reasoned rerouting: spec 064 SCOPE-17 pointed `/ask` at the open-ended
   agent so users get web search plus internal retrieval plus tools, with `internal_retrieval`
   registered as a tool *inside* `open_knowledge` so the user's own corpus is still queried
   first. The registry entry predates that and was never updated. Choosing it would remove
   capability from a shipped token to satisfy the newer of two stale records.
2. *Retire `/recipe` and `/cook`.* Rejected. Both work today. Deleting working user-visible
   tokens to make a comment true is the wrong direction of repair.
3. *Let generation order decide.* Rejected explicitly — `scopes.md` SCOPE-06 already names
   this: "resolved by an explicit recorded decision, not silently by generation order."
4. *Route the whole question to the operator.* Considered seriously and rejected. Both
   sub-decisions resolve to "keep what currently ships", so neither changes user-visible
   behaviour, and a decision that changes nothing observable does not need operator
   adjudication. The moment either direction *would* change behaviour, it does — see the
   consequence.

**Reasoning.** Where two records disagree and one of them is running code that users are
using, the running code is the fact and the other record is the drift. That rule is
decidable without product input and gives the same answer both times here.

**Consequence.** Zero user-visible behaviour change from resolving the contradiction, which
is the desired outcome for a registry that is supposed to describe the system rather than
change it. **If the operator wants `/ask` to mean corpus-only retrieval, that is a separate,
explicit product change** — it must not arrive as a side effect of this feature's generation
step. `SCOPE-06` owns the token-uniqueness invariant.

### D6 — Who performs the navigation cutover · `F-112-CUTOVER-01`

**Decision.** **Spec 106 performs the cutover. Feature 112 does not.** 112 declares the
guaranteed core as descriptor facts and validates them; 106 wires the projection into the
server, PWA and card renderers and retires the three handwritten authorities.

**Alternatives considered.**

1. *112 performs the cutover.* Rejected on ownership and on evidence. Spec 106 is
   `in_progress`, its `SCOPE-106-04/05` are the named cutover scopes, and
   `internal/experience/catalog.go:10` records the deferral in the package's own doc comment.
   `navigation_projection.go` already exists as "the content-free data model the shared-shell
   cutover will LATER wire into the server, PWA, and Card renderers". 112 doing it would be a
   second spec editing 106's scopes' surface.
2. *Neither performs it; both defer.* Rejected. That is how the "ALONGSIDE" state became
   permanent in the first place, and R-112-09 would be satisfied by nobody.
3. *112 performs it only for the digest.* Rejected. A one-capability cutover leaves two
   navigation code paths — generated for one entry, handwritten for the rest — which is
   strictly worse than either end state.

**Reasoning.** The cutover is renderer-wiring work on a live shell; the registry is
identity-and-policy work. They are different changes with different regression surfaces, and
106 already owns the first and has built its model.

**Consequence — recorded honestly, because it narrows this feature's own scope.**
`SCOPE-05` becomes *declare and validate the guaranteed core*, not *cut it over*, and
`SCOPE-09`'s retirement obligation covers only the surfaces 112 itself projects (intent,
alias, external) — not the three navigation authorities. R-112-09 for the navigation surface
is discharged by spec 106. **[`scopes.md`](scopes.md) still describes SCOPE-05 and SCOPE-09 in
the wider form and is owned by `bubbles.plan`; this narrowing is routed to that agent rather
than applied here.** The cross-train consequence is `OD-112-03`.

### D7 — The external tool projection without passthrough · `F-112-109-01`

**Decision.** The external projection is **opt-in per descriptor and absent by default**. A
capability appears in it only if its record carries an `external_tool:` block declaring the
tool name, a description written for a foreign client, the input and output contract it
honours, and the grant required. No block means no export. There is no "export everything
user-facing" rule.

**Alternatives considered.**

1. *Export every `user_facing` capability.* Rejected. That is a blanket export under a
   different name, and `scopes.md` SCOPE-07 already forbids "a blanket export of the
   capability set".
2. *Derive from `agent.All()`.* Rejected — spec 109 names this prohibition literally
   (`spec.md:80-81`): "no MCP tool is derived by passthrough from `agent.All()`".
3. *Let spec 109 keep its own hand-maintained tool list.* Rejected. It is inventory #4 of the
   four this feature exists to eliminate; leaving it hand-maintained means the feature
   removed three of four and declared success.

**Reasoning.** Spec 109's prohibition is about *derivation*, not about *generation*. A
projection whose membership is decided by a field an author deliberately wrote is an authored
export list that happens to be machine-rendered. A projection whose membership is decided by
"a tool is registered" is passthrough. The declared block is on the correct side of that line,
and the `external_tool.grant` field is what makes the export a grant decision under
Principle 11 rather than a generation side effect.

**Consequence.** `SCOPE-07` produces a projection that may legitimately be **empty** at first
— zero capabilities opted in — and an empty projection is a correct outcome, not a missing
one. Combined with `D9`, a capability that opts in but whose grant is unenforceable is
withheld, so the projection is `opted-in ∩ enforceable`.

### D8 — What the guaranteed core guarantees on a surface rendering no navigation · `F-112-ISLANDS-01`

**Decision.** Two parts, and the second is what stops the first being vacuous:

1. **Scope.** The guarantee binds surfaces that render navigation. 112 does not retrofit
   navigation onto the 29 island pages (Non-Goal 6). The set of non-rendering surfaces
   becomes a **declared, enumerated** fact (R-112-22), so "where the core does not reach" is
   answerable rather than unknown.
2. **Strength.** Core membership is asserted **per renderer**, not per abstract "core". The
   descriptor declares `navigation: { core: true, renderers: [server, pwa, card] }`, and the
   check asserts presence for **each named renderer**.

Part 2 is what makes the guarantee falsifiable today. The `today` surface — the digest —
declares `renderer_support: [server]` (`config/smackerel.yaml:2787-2798`). A core assertion
that only asked "is the digest in the core" would pass against today's tree. A per-renderer
assertion fails, because the digest is absent for `pwa`. That failure is the correct current
answer and is exactly finding `D18`.

**Alternatives considered.**

1. *Guarantee the core on every surface including the islands.* Rejected. It requires shell
   composition on 29 pages, which is Non-Goal 6 and belongs to the shell spec.
2. *Guarantee only on navigation-rendering surfaces, with no per-renderer assertion.*
   Rejected — this is the vacuity `F-112-ISLANDS-01` warns about, and it would pass today
   while the defect is live.
3. *Treat the server shell's own appended digest link (E14) as core membership.* Rejected.
   R-112-21 forbids exactly this, and `spec.md`'s `D18` precision note preserves the
   distinction between "reachable somewhere" and "in the guaranteed core".

**Reasoning.** A guarantee whose assertion cannot fail against the tree that motivated it is
not a guarantee. Binding it to `renderer_support`, which already exists and is already
generated, makes the assertion concrete without inventing a new mechanism.

**Consequence.** Satisfying R-112-19 requires `today` to gain `pwa` renderer support, which
is renderer work owned by spec 106 per `D6`. 112 declares the requirement and ships the check
that fails until 106 satisfies it. That is the intended relationship: the registry makes the
gap measurable; the shell closes it.

### D10 — Withholding a capability without leaking its existence

**Decision.** Two channels, deliberately asymmetric:

| Channel | Audience | Content when a capability is withheld |
|---|---|---|
| The projection | The principal | **Nothing.** No entry, no label, no placeholder, no count. |
| The diagnostic channel | Operator only | Capability id, the grant it declared, and the reason (`grant-not-enforceable`, `exposure-withheld`, `unknown-grant`) — in the coverage-check output and a server-side log/metric. |

**Alternatives considered.**

1. *Reuse the existing `unavailable_pending_*` presentation.* Rejected, and this is the
   subtle one. That policy keeps the surface's **label** and drops its href, which is right
   for "not built yet" — the user learns the product intends to have it. It is wrong here:
   the thing NFR-112-06 protects is the *existence* of a capability the principal is not
   permitted to know about. Reusing the pattern would leak by design.
2. *A generic "some capabilities are unavailable" notice.* Rejected. A count is an oracle:
   it changes as capabilities are added, and it confirms that something exists to be hidden.
3. *Report the reason to the principal.* Rejected. It is the leak, stated plainly.
4. *Log nothing at all.* Rejected. R-112-25 requires the reason to be **reported**, and an
   operator debugging "why is this capability missing" with no signal will conclude the
   registry is broken and work around it.

**Reasoning.** "Report the reason" and "do not leak the existence" are only in tension if
they share an audience. Splitting the audience satisfies both without weakening either.

**Consequence.** `SCOPE-03` and `SCOPE-07` both carry a DoD item asserting absence leaks
nothing; the corresponding test must assert on the **projection payload**, not on log output,
or it proves the wrong half.

## The Capability Descriptor

Authored shape in `config/smackerel.yaml` under `product_experience.capabilities:`. Field
presence rules are stated as requirements on the generator; a missing required field is a
generation error with no default (P3, R-112-17).

| Field | Required | Meaning | Requirement |
|---|---|---|---|
| `id` | always | Stable identity, `cap.*`. Never changes when phrasing, navigation, alias or exposure changes | R-112-01, R-112-03 |
| `label` | always | Human wayfinding label | R-112-02 |
| `owning_service` | always | The domain service that implements it | R-112-02 |
| `exposure` | always | One of the five closed classes (`D4`) | R-112-13 |
| `exposure_reason` | when `exposure != user_facing` | Non-empty prose; whitespace rejected | R-112-14 |
| `dispatchable` | always | `true` for an invocable capability, `false` for a pipeline stage | R-112-15 |
| `contracts` | always (may be `[]`) | Prompt-contract ids bound to this capability, 0..N (`D1`) | R-112-02 |
| `surfaces` | always (may be `[]`) | Catalog surface ids; must agree with the reverse `capability_id` edge | R-112-06 |
| `side_effect_class` | always | `read` \| `write` \| `external`, reusing `agent.SideEffectClass` | R-112-27 |
| `requires_provenance` | always | Whether output must cite sources | R-112-28 |
| `authorization.principal` | when reachable | The authenticated principal required | R-112-23 |
| `authorization.grants` | when reachable (may be `[]`) | Grants required, drawn from spec 108's vocabulary; never redefined here | R-112-23, R-112-26 |
| `intent` | when `exposure: user_facing` | Natural-language phrasing basis (see the no-restatement rule) | R-112-02, R-112-29 |
| `alias` | optional | Slash tokens, 0..N; many→one legal, one→many forbidden (`D5`) | R-112-02 |
| `navigation.core` | always | Whether it is a guaranteed-core member | R-112-19, R-112-20 |
| `navigation.renderers` | when `core: true` | The renderers the core must reach (`D8`) | R-112-20 |
| `external_tool` | optional | Opt-in external export block; absent means not exported (`D7`) | R-112-02, R-112-25 |
| `evaluation_case` | when `exposure: user_facing` | Reference to the case that exercises it | R-112-29 |

**Content-free discipline (P9, R-112-07).** No user content, no readiness fact, no session
scope. The descriptor may say a capability *requires* `corpus:read`; it may never say whether
a given principal *holds* it. The existing catalog holds the same line and states it in its
own package doc comment.

## Identity, Binding, And The No-Restatement Rule

R-112-04 says no reachability surface may carry a capability fact absent from the descriptor.
That leaves a genuine question the requirements do not settle: some facts **already exist on
the contract**, and `agent.Scenario` already carries `IntentExamples` and `SideEffectClass`
(`internal/agent/loader.go:49-77`).

**Rule.** Where a fact already has exactly one authoritative home in a built artifact, the
descriptor **references** it and the coverage check **asserts agreement**. Where it has none,
the descriptor **authors** it.

| Fact | Home | Descriptor's role |
|---|---|---|
| Intent phrasing | `intent_examples` on the contract | References the contract; the check asserts a `user_facing` capability's bound contract has non-empty examples |
| Side-effect class | `side_effect_class` on the contract | References for bound contracts; **authors** for a 0-contract capability, which has no contract to carry it |
| Grant vocabulary | `internal/auth/scopes.go` | References only; redefining it violates R-112-26 |
| Exposure class | nowhere | **Authors** — this is the fact the feature exists to create |
| Navigation core membership | nowhere | **Authors** |
| Alias | contradicted in two places | **Authors**, adjudicated by `D5` |
| External export | nowhere | **Authors** (`D7`) |

The alternative — copying `intent_examples` into the descriptor — was rejected because it
creates the two-records-one-fact defect this feature removes, with the contract and the
descriptor able to disagree exactly as `scenarios.yaml` and `shortcuts.go` do today.

## The Projection Contract

Every projection is a pure function of the capability set plus the admission predicate:

```
project : (Capabilities, Predicate, SurfaceKind) → OrderedProjection
```

Foundation-owned obligations, identical for all four:

- **Determinism** (NFR-112-01). Same input, byte-identical output, so a regenerated
  projection reviews as a diff.
- **Stable ordering** (NFR-112-04). Ordering derives from an authored key, never from map
  iteration. The existing package already sorts before emitting for exactly this reason.
- **Fail-closed** (P4). On any inconsistency the projection returns a typed error and emits
  nothing. It never emits a partial projection with the bad entry dropped, because a silently
  dropped entry is how a capability becomes unreachable without anything failing — the
  feature's founding defect.
- **Admission** (`D9`). The predicate is applied by the foundation, not re-implemented per
  projection, so no projection can accidentally admit what another withholds.
- **No leak** (`D10`, NFR-112-06). A withheld capability contributes nothing to the payload.

Per-projection differences are enumerated at `### Variation Axes`.

## Authorization And The Enforcement Predicate

- Authorization is **server-derived** (R-112-24). The descriptor names the requirement; the
  server resolves the authenticated principal's grants. Caller-asserted authority is never
  read. This is the existing posture in `internal/auth/`; 112 adds no new trust path.
- The grant vocabulary is **consumed** from `internal/auth/scopes.go` (R-112-26). A
  descriptor naming a grant outside that vocabulary is a coverage-check violation
  (`unknown-grant`), which is also the mechanism that catches a typo becoming a permanently
  withheld capability.
- **Enforceability** is the third conjunct of the admission predicate (`D9`), read from
  `internal/api/corpus_grant_gate.go`'s startup-resolved stage. `observe` withholds;
  `enforce` admits.
- A capability declaring **no** grants is unaffected by the stage. The predicate's third
  conjunct applies only to grant-requiring capabilities, so navigation-only capabilities such
  as `cap.settings` are not withheld by an unrelated boundary.

`check-did-not-run` is not decorative. Producer (b) needs a live stack and will skip without

## Versioning And Compatibility

| Concern | Rule |
|---|---|
| Schema version | `smackerel-product-experience/v2`. A shape change without a version change is forbidden; `GeneratedCatalog()` already rejects an empty version and gains a capability-emptiness check |
| Capability id stability | `cap.*` ids are permanent (R-112-03). Phrasing, navigation, alias and exposure may change freely; the id may not |
| Retirement | A retired capability is **removed from the registry only after it is removed from the built system**. Removing the descriptor first makes it `unregistered-capability` — correctly, since it is still built and now undeclared |
| Renaming | Not supported as an in-place edit. A rename is a new id plus a retirement, so the old id never silently acquires new meaning |
| Contract rebinding | Moving a contract between capabilities is legal; both descriptors change in one edit, and `contract-claimed-twice` catches a half-done move |
| Grant vocabulary changes | Owned by spec 108. A grant leaving that vocabulary surfaces here as `unknown-grant` rather than as a silent widening |
| Backward compatibility of projections | The projections replace hand-maintained inventories that have no version. Compatibility is asserted by the projection reproducing current behaviour except where a decision (`D5`) records otherwise |

## The Feature Flag

**Name:** `capabilityRegistryProjections`. **Owning train:** `next`. **Default:** OFF in
every train at introduction, following the `corpusGrantEnforcement` and `clientReleaseLaneB`
precedent already in both bundles.

Semantics — what the flag gates, precisely:

- **OFF:** the capability block is generated and validated, the coverage check runs, and
  **no projection drives any live surface**. The existing intent registry, navigation
  authorities and slash table remain in force unchanged. This is the `mvp` behaviour
  `spec.md` `## Release Train` already describes.
- **ON:** the projections become the source for the surfaces 112 owns (intent, alias,
  external). Navigation remains 106's per `D6`.

The flag deliberately does **not** gate the coverage check. A check that only runs when the
feature is enabled cannot report drift on the train where the hand-maintained inventories are
still live — which is the train where drift actually happens.

**What this design cannot do:** author the two bundle entries. `config/feature-flags.mvp.yaml`
and `config/feature-flags.next.yaml` are owned by `bubbles.train` and are outside this
authoring run's permitted surface, so `flagsIntroduced` stays empty rather than declaring a
flag with no enforcement behind it. Routed as `OD-112-02`; `F-112-FLAG-01` stays BLOCKING.

## Testing And Validation Strategy

The Test Matrix in [`scopes.md`](scopes.md) is owned by `bubbles.plan`. What design fixes is
which behaviours must be provable and why a weaker test would not prove them.

| Behaviour | Category | Why a weaker test fails to prove it |
|---|---|---|
| Independence of the universe | `integration` | A unit test can construct any universe it likes. Independence is a property of the derivation path, so the test must run the real producers and assert the no-import rule |
| Coverage check can fail | `unit` + adversarial | A check asserted only on a clean registry proves nothing. The adversarial case removes one facet and requires failure — this is the direct antidote to E9 |
| Core membership | `integration` per renderer | An abstract "digest is in the core" assertion passes against today's `renderer_support: [server]`. Per-renderer is what makes it fail correctly (`D8`) |
| Grant withholding | `e2e-api` | The assertion must read the **projection payload**, not logs. Asserting on logs proves the reason was recorded, not that the capability was hidden (`D10`) |
| Alias uniqueness | `integration` | Must span every surface. A per-surface test passes today: each file is internally consistent and they disagree with each other (E15) |
| One-edit reachability | `e2e-api` | Must assert the hand-maintained inventories were **not modified**. Otherwise it proves reachability, not single-edit reachability |
| Determinism | `unit` | Regenerate twice, compare bytes. A structural-equality assertion permits ordering drift, which NFR-112-04 forbids |

**Test-data posture.** Every live-category test uses ephemeral storage per the repository's
test-isolation policy. The capability set under test is a fixture, never the shipped
`catalog.gen.json`, so an adversarial fixture can be malformed on purpose.

## Constraints The Design Could Not Trade Away

- **Extend, never duplicate** (P5, Non-Goal 1) — discharged structurally by `D3`: one SST
  block, one generator step, one output file, one embed, one package.
- **Every surface is generated** (P2, R-112-08) — discharged for intent, alias and external
  by 112; for navigation by spec 106 per `D6`, recorded rather than quietly dropped.
- **Exposure is declared, never defaulted** (P3, R-112-13) — discharged by `D4`'s required
  key and no-usable-zero-value type.
- **Reach never outruns the guard** (P4, R-112-25) — discharged by `D9`'s runtime predicate
  rather than by scheduling.
- **Coverage against an independent universe** (P6, R-112-31) — discharged by `D2`, with the
  no-import rule as its mechanical form.
- **The registry is content-free** (P9, R-112-07) — the descriptor may state a requirement,
  never a holding.
- **The grant vocabulary is consumed, not redefined** (R-112-26, Non-Goal 2) —
  `unknown-grant` enforces it.

## Capability Foundation

**The heavy shape is correct here, and this pass confirms it rather than inheriting it.** The
test applied was whether the four reachability surfaces genuinely differ along more than one
real axis, or whether they are one thing described four times. They differ along five axes
with distinct consuming code, distinct admission rules, distinct enforcement points, distinct
invariants and distinct retirement costs — enumerated with citations at `### Variation Axes`.
This is the opposite of the sibling spec 111, where a single egress chokepoint correctly took
the single-implementation branch.

**The foundation is the CapabilityDescriptor record plus the Projection contract**: the one
place a capability fact is authored, and the rule that every reachability surface is derived
from it rather than authored beside it.

Foundation-owned, identical for every projection, and fixed by this pass:

| Foundation element | Fixed by | Requirement |
|---|---|---|
| The descriptor's field set and presence rules | `## The Capability Descriptor` | R-112-02 |
| The unit of record and its binding cardinality | `D1` | R-112-01 |
| Identity stability across phrasing / navigation / alias / exposure change | `D1`, `## Versioning And Compatibility` | R-112-03 |
| Where the record lives and how it is generated | `D3` | R-112-05 |
| The closed exposure vocabulary and its reason rule | `D4` | R-112-13, R-112-14 |
| The no-restatement rule for facts a contract already owns | `## Identity, Binding, And The No-Restatement Rule` | R-112-04 |
| The admission predicate, applied once, not per projection | `D9` | R-112-25 |

| Side-effect class and provenance requirement travelling with the record | `## The Capability Descriptor` | R-112-27, R-112-28, P8 |

## Concrete Implementations

Four projections over one foundation. Each consumes the descriptor set and the shared
admission predicate, and adds nothing to the record.

| Concrete Implementation | Surface it projects onto | Predecessor to retire (R-112-09) | Owning scope | Decision that shapes it |
|---|---|---|---|---|
| Assistant intent projection | The natural-language intent set | `config/assistant/scenarios.yaml` (inventory #1) | SCOPE-04 | `D9` admission; no-restatement rule for `intent_examples` |
| Navigation core projection | The guaranteed cross-surface core, digest included | Three live, already-divergent authorities (E11 – E14) — **retired by spec 106, not by 112** | SCOPE-05 | `D6` ownership; `D8` per-renderer assertion |
| Alias projection | The slash token table | `internal/assistant/shortcuts.go` (inventory #3) | SCOPE-06 | `D5` adjudication; many→one legal, one→many forbidden |
| External tool projection | The external tool list | none — not built (spec 109) | SCOPE-07 | `D7` opt-in block; `D9` ∩ enforceable |

**Assistant intent projection.** Emits the set a natural-language matcher consumes.
Membership: `exposure == user_facing` and the admission predicate holds. Phrasing is
**referenced** from the bound contract's `intent_examples`, not copied (no-restatement rule).
Must preserve the honest no-match path of UC-112-001: when nothing matches with sufficient
confidence, the user is told so and is never silently handed a different capability.

**Navigation core projection.** Emits the guaranteed core with per-renderer membership
(`D8`). Membership: `navigation.core == true`, projected once per entry in
`navigation.renderers`. **112 emits and validates; spec 106 wires it into the renderers**
(`D6`). Its check fails against today's tree, because `today` declares
`renderer_support: [server]` while the core requires `pwa` — that failure is finding `D18`
made mechanical.

**Alias projection.** Emits the token table. Membership: the capability declares at least one
`alias` and the predicate holds. Enforces token uniqueness by construction — a token maps to
exactly one capability, so E15's two-target contradiction becomes unrepresentable rather than
merely detected. `D5` fixes the two adjudications the generator would otherwise make by
ordering.

**External tool projection.** Emits the tool list a foreign client discovers. Membership: an
`external_tool` block is present **and** the predicate holds — that is,
`opted-in ∩ enforceable`. Absence of the block means absence from the projection (`D7`). May
legitimately be empty. Its admission is itself a grant decision under Principle 11, which is
why it is the only projection whose membership rule is a security decision rather than a
presentation one.

### Variation Axes

Five axes. Each is a real difference with a citation, not a category invented to fill a
heading. Axes 1, 2 and 4 are structural; axes 3 and 5 are the ones that make a single shared
implementation actively wrong rather than merely awkward.

- **Axis 1 — Consuming surface and input shape.** A natural-language matcher, a rendered
  shell, a token parser, and a protocol client. Four distinct `ReachabilitySurface` instances
  (`spec.md` §4.1), one descriptor set (R-112-08). The output types are not interchangeable:
  an ordered navigation tree and a flat token map are different structures, not different
  formats of one structure.
- **Axis 2 — Admission rule.** Each projection admits a different subset of the same set.
  Intent admits on `exposure == user_facing`; navigation on `navigation.core` per renderer
  (R-112-19 … R-112-22); alias on the presence of a token; external on an opt-in block
  (`D7`). A `test_only` capability is admitted by none (R-112-16, SCN-112-B04). Shared
  record, per-projection filter.
- **Axis 3 — Where the authorization decision sits.** P4 binds all four, but not at the same
  point. For the external projection, **admission is itself the grant decision** under
  Principle 11 — being listed is being granted. For intent and alias, admission is
  presentation and the guard applies at dispatch. For navigation, admission is
  discoverability and the route re-checks independently — the posture
  `navigation_projection.go` already documents, where an operator-only surface is omitted
  from a daily user's visible projection yet its route still exists and still re-checks
  authorization. Three different enforcement points; `F-112-108-01` is BLOCKING on this axis
  alone.
- **Axis 4 — The invariant each must hold.** Navigation: an ordered core with cross-surface
  parity (R-112-20, R-112-21, NFR-112-04). Alias: token uniqueness — the invariant the
  shipped code violates today (E15, E16). Intent: an honest no-match path (UC-112-001).
  External: per-capability declared naming, because passthrough derivation is forbidden
  (E19). No single invariant covers all four, and each is falsifiable independently.
- **Axis 5 — Retirement cost and owner.** R-112-09 obliges each projection to retire its
  hand-maintained predecessor, and the obligations are not comparable. Intent and alias each
  replace one authority and are retired by 112's SCOPE-09. Navigation must reconcile three
  divergent authorities across two renderers and is retired by **spec 106**, on a different
  train (`D6`, `OD-112-03`). External has no predecessor and retires nothing. A shared
  retirement implementation would have to be simultaneously a no-op, a single-file removal,
  and a cross-spec cross-train cutover.

## Open Decisions Requiring Operator Input

Three. Each records the exact question and the exact fact that would close it. None is
invented to fill a heading, and none is a design question wearing an operator costume.

### OD-112-01 — The exposure class of each of the eleven undeclared dispatchable capabilities

**Question.** For each of `alert_timing_evaluate`, `annotation_classify`,
`expertise_classify`, `hospitality_concern_evaluate`, `recommendation_feedback`,
`recommendation_reactive`, `recommendation_watch_evaluate`, `recommendation_why`,
`relationship_cooling_evaluate`, `resurface_evaluate`, `retrieval_evergreen` — which of the
five classes (`D4`) applies, and for the four non-`user_facing` classes, what is the reason?

**Why it is not design's call.** `spec.md` Non-Goal 4 already assigns it: "Which class each
of the eleven receives is an operator and design decision, recorded per capability, not fixed
here." Several are plausibly `internal` (a watch evaluator invoked by a scheduler rather than
by a user), several plausibly `user_facing` (asking why a recommendation was made). Choosing
by plausibility would be exactly the guess the registry exists to replace with a declaration.

**What closes it.** An operator decision per capability. `D4` supplies the vocabulary and the
reason requirement, so each answer is one class plus one sentence.

**Consequence while open.** `SCOPE-02` can build the vocabulary, the requiredness rule and
the check; it cannot complete its DoD item "each of the eleven carries an explicit class and,
where not user-facing, a reason".

### OD-112-02 — The `capabilityRegistryProjections` flag-bundle entries

**Question.** Add `capabilityRegistryProjections: false` to both
`config/feature-flags.mvp.yaml` and `config/feature-flags.next.yaml`, with
`introduced_in_train: next` metadata, following the `corpusGrantEnforcement` precedent
already present in both files?

**Why it is not design's call.** This design fixes the flag's name and semantics — that part
*is* design and is recorded at `## The Feature Flag`. Authoring the bundle entries is not:
both files are owned by `bubbles.train`, gate G111 requires an introduced flag to be
default-OFF in every non-owning train's bundle, and this authoring run's permitted surface is
`specs/112-capability-registry/` only. Naming the flag in `flagsIntroduced` without the
backing entries would produce a declaration that reads as enforced and is not.

**What closes it.** `bubbles.train` adding the two entries, after which `flagsIntroduced`
becomes `["capabilityRegistryProjections"]`.

**Consequence while open.** `flagsIntroduced` stays `[]`. `F-112-FLAG-01` stays BLOCKING.

### OD-112-03 — Sequencing 112 (`next`) against spec 106 (`mvp`)

**Question.** `D6` places the navigation cutover with spec 106 and `D8` requires the digest
to gain `pwa` renderer support — both spec 106 work, on train `mvp`. Feature 112 targets
`next`. How are they sequenced: does 106 complete its cutover on `mvp` first, does the digest
work move to `next` with 112, or does 112 ship its navigation check in a
failing-but-declared state until 106 lands?

**Why it is not design's call.** Train assignment and cross-train sequencing are release
decisions. `spec.md`'s `## Release Train` section justifies `next` for 112 on
security-posture grounds that remain valid, and spec 106's `mvp` assignment is equally sound
for shell work. The conflict is between two correct choices and is resolved by release
planning, not by design.

**What closes it.** A `bubbles.plan` / `bubbles.train` sequencing decision, or a train change
on either spec.

**Consequence while open.** `SCOPE-05` is buildable and its check is authorable, but the
check *passing* depends on a spec on another train. If the answer is "ship the check
failing", that must be an explicit recorded choice — a permanently red check is corrosive,
and `spec.md` §2 already warns against the class of validation that stops meaning anything.
